## Pairing

Barreiras confirmadas no código:

- Pairing v1 fica fechado em Production até `NEXUS_WORKER_PAIRING_V1=1`.
- Preview pode habilitar o fluxo explicitamente por `VERCEL_ENV=preview`.
- Endpoint de criação exige usuário autenticado.
- Endpoint exige same-origin.
- Criação possui rate limit por usuário.
- Código temporário segue formato restrito, possui TTL máximo de 600 segundos e é de uso único.
- Somente SHA-256 do código é persistido.
- O gateway gera uma nova credencial `nxw1_` aleatória e persiste somente seu SHA-256.
- RPCs de pairing revogam EXECUTE de `public`, `anon` e `authenticated`; somente `service_role` executa.
- Heartbeat, claim e finish exigem bearer `nxw1_`.
- Worker runtime permanece restrito a JSON/Markdown; shell, `child_process`, `eval`, Docker e browser automation não fazem parte do runtime permitido.

## Riscos / pendências de segurança

### 1. Rate limit de pairing é local ao processo

O rate limiter da aplicação é em memória. Em execução horizontal, o limite não é compartilhado entre instâncias.

**Impacto:** abuso de criação de códigos pode ser distribuído entre instâncias.

**Ação recomendada:** proteção compartilhada de borda/WAF ou armazenamento distribuído antes de ampliar o fluxo.

### 2. Service role mantém blast radius elevado

As rotas server-side usam a chave privilegiada do Supabase para RPC/REST. O desenho atual mantém a chave fora do cliente, mas qualquer futuro bypass de autorização numa rota pode transformar um bug de aplicação em acesso privilegiado.

**Ação recomendada:** manter o isolamento `server-only`, limitar RPCs por contrato e continuar evitando acesso direto do navegador às tabelas/RPCs protegidas.

### 3. Gateway não possui rate limit próprio

Depois que um token `nxw1_` é obtido, heartbeat/claim/finish dependem essencialmente da credencial e das regras transacionais do banco.

**Impacto:** token comprometido pode gerar tráfego e tentativas repetidas até ser desabilitado/invalidado pelo backend.

**Ação recomendada:** rate limiting por credencial/worker no gateway ou camada de borda, sem alterar o protocolo de pairing nesta PR.

### 4. E2E físico ainda não está fechado

A documentação identifica como gate pendente o primeiro worker físico e o fluxo completo Studio → pairing → heartbeat → enqueue → artifact → audit.

**Impacto:** build verde não comprova o protocolo completo com um worker real.

**Ação necessária:** executar o primeiro teste físico controlado em Preview.

### 5. Builder RPC hardening continua pendente

O próprio README lista o rollout coordenado do Builder RPC hardening como pendência.

**Ação necessária:** tratar separadamente, sem misturar com esta revisão de pairing.
